# 민감정보 마스킹 (V1-85) — 구현 전 정리

대상: 회원 이름 · 전화번호 · 이메일. 내일 아침 착수 전 확인한 현재 상태와
필요한 결정들.

## 확인된 현재 상태

- AI 질의응답 전체(FEATURE_SPEC.md F9, V1-71~85)가 **미착수**다. `ask.py`,
  `knowledge/{chunker,embedder,vector_store}.py` 전부 `NotImplementedError`
  스텁. 즉 마스킹을 끼워 넣을 파이프라인 자체가 아직 없다.
- `profiles` 테이블(`supabase/migrations/20260914000000_profiles.sql`)에
  **전화번호 컬럼이 없다.** "번호"가 전화번호라면 마스킹 이전에 수집·저장
  경로부터 없는 상태.
- `ai-service/logs/log.jsonl` 비어 있음 — 아직 아무것도 안 쓴다.
- LLM 제공자 미정 (`openai` 참조는 `embedder.py`/`pyproject.toml`뿐, 실제 호출
  코드 없음).

## 마스킹만으로 안 끝나는 이유

정규식 치환은 마지막 한 줄이고, 그 앞에 결정할 게 먼저다.

1. **탐지 방식** — 이메일·전화번호는 정규식으로 잡히지만, 이름은 정규식으로
   못 잡는다(문맥 의존). 프로필의 `fullName` 값과 직접 매칭하는 방식이 현실적.
2. **적용 지점** — 마스킹은 "어디서"가 핵심. 지점마다 목적이 다르다(아래 표).
3. **저장 정책** — DB엔 원문 저장하고 노출 시점에만 마스킹할지, 저장 자체를
   마스킹본으로 할지. 후자면 원문 조회가 영영 불가능(비가역)하다는 뜻.
4. **가역성** — 관리자가 원문을 볼 일이 있는지 여부가 위 정책을 정한다.

## 적용 지점 후보

| 지점 | 코드 위치(예정) | 필요성 |
|---|---|---|
| LLM 프롬프트 조립 직전 | `ai-service` LLM 호출 함수 | 외부 API로 원문이 나가는 것 자체를 막음 — 가장 중요 |
| 대화 이력 저장 (V1-81) | `ai-service` 또는 Next 저장 로직 | DB 유출 시 피해 최소화 |
| `ai-service` 로그 (`log.jsonl`) | `app/core` 로깅 wrapper | 로그 파일이 PII 저장소가 되는 것 방지 |
| 관리자 화면 표시 | (아직 없음) | 나중 |

## 스키마 갭

"번호"가 전화번호라면 `profiles`에 컬럼 추가 마이그레이션부터 필요하다 —
이게 이번 작업 범위에 들어가는지 먼저 확인. (AGENTS.md: 컬럼 추가 시 RLS
정책도 같은 커밋에.)

## 내일 아침 순서 제안

1. 위 4가지 결정(탐지 방식/적용 지점/저장 정책/가역성) 확정.
2. 마스킹 함수를 순수 함수로 구현 (`ai-service/app/domain/` — AGENTS.md 순수
   함수 테스트 규칙, `assert` 기반 테스트 1개).
3. LLM 호출 직전 지점부터 적용 — 파이프라인 자체가 없으므로 F9 본체 구현과
   묶어서 진행하게 될 가능성이 큼.
4. 로그/저장 지점은 그 뒤에 이어서.
