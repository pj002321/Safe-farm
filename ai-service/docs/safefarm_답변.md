## 1\. 작물 종류를 얼마나 추천해줄 수 있고 그 종류 양은 얼마나 감당가능한지?

* 작물은 데이터베이스를 늘리면 그만큼 추천 가능할거라 생각됩니다. 농사로의 농작업일정파일만 현재 다운로드 받은 상태인데, 작물 중복을 고려하면 100개정도 있는 것 같습니다. 품종으로 세밀하게 들어가면 더 많아지는데 그 정도는 현재 시간상으로 감당이 불가능할 것으로 보입니다.
* 작물 하나에 다음과 같은 데이터가 필요합니다

  * 기준온도        GDD 계산할 때 빼는 값
  * 목표 적산온도    이만큼 쌓이면 수확
  * 생육단계 구간    발아기 몇 도부터 몇 도까지
  * 단계별 할 일     이때 물 주고 이때 웃거름
* 농작업 일정 파일에 기준온도, 적산온도, GDD 외의 데이터가 있는것을 확인하였습니다. 두 값은 농작업일정 내부의 데이터와 기상청 실측 기온 자료를 이용해 생성할 수 있다고 합니다. 

그 외에 api로 요청가능한 농업관련 데이터가 있음을 확인하여 현재 신청해둔 상태입니다.

GDD 관련 논문은 아직 찾아보지 않아 이후 보완하도록 하겠습니다 



## 2\. 위성, 기후 데이터를 어떻게 가져와서 실시간으로 추천해주는지

* 실시간보다는 하루 주기로 보는게 낫습니다. 날씨예보나 GDD도 하루 단위로 변동되기 때문입니다.

```
데이터 수집 및 갱신 방식

\[기상 데이터 - 1차 사용]
출처: 기상청 API허브 / Open-Meteo
방식: 매일 새벽 1회 자동 실행(배치)
     → 텃밭 좌표별 최고/최저기온·강수량 수집
     → DB에 저장
     → 누적 GDD 갱신

\[위성 데이터 - 2차]
출처: Copernicus (Sentinel-2)
방식: 5일 주기 관측이라 매일 갱신 불가
     구름 낀 날은 결측 처리

\[실시간이 아닌 이유]
날씨와 생육은 하루 단위로 변하므로
매 접속마다 API를 호출할 필요가 없습니다.
미리 계산해두면 화면은 즉시 뜨고, API 호출 비용도 줄어듭니다.
```



였는데? API 이것저것 받고 다른 방안 이것저것 찾다보니 다른 길도 찾았습니다.

아래는 클로드 왈 입니다.



> \*\*\[정정] 격자 변환이 필요 없어졌습니다\*\*
>
> 처음엔 공공데이터포털 단기예보를 쓸 계획이라 `dfs\_xy\_conv`로 격자 변환이 필요했는데, 실제로 승인받은 것은 \*\*기상청 API허브\*\*였고 여기는 관측소 번호(`stn`)로 조회합니다. Open-Meteo는 좌표를 그대로 받고요.
> ```
> 기상청 API허브   stn=137 (상주)
> Open-Meteo      latitude=36.4084\&longitude=128.1574
> ```
> 격자 변환 로직이 빠지므로 텃밭 등록 화면(V1-17)도 단순해집니다.



\---



이어서



* 현재 사용하기에 용이한 위성 데이터는 다음과 같습니다
* Sentinel-2 (EU)     10m      5일 주기
* 천리안 2A (KR)      1km      2분





* 그리고 위성은 아니지만 Open-Meteo (한국, 일본(한국과 가까움), 유럽중기예보센터(정확도가 가장 높음)) 사용을 제안합니다.

  : 한국의 일기예보 데이터의 경우 클레임이 많은 편이라 다소 과장된 예보가 많다는 이슈가 있어 농민들도 국내 기상 데이터 불신자가 많습니다. 때문에 어떤 농민들은 국외의 기상데이터를 농업에 참고합니다.

  주로 사용하는 건 일본의 위성데이터라고 하는데.. 일단 가능성만 확인하고 제대로 데이터를 뜯어보진 않았습니다. 

  open meteo 사용을 제안한 이유는 지인이 사용중인 어플이 이것을 기반으로 하고있는데, 유용하게 사용하고 있다는 말을 들었기 때문입니다. api는 필요없습니다.

  Open-Meteo는 수치예보 모델로, ECMWF·NOAA·DWD·\*\*JMA\*\*·\*\*KMA\*\* 등 15개 이상 기상청의 모델을 모아 제공합니다. 지인분이 보시는 일본 예보도 여기서 `jma\\\_gsm` 모델로 받을 수 있습니다. \*\*한 좌표에 한국·일본·유럽 예보를 나란히 놓고 비교\*\*할 수 있다는 뜻입니다.

  \---



* 기상청 api : 활용 신청목록

  * 천리안2A, 지상관측, 태풍, 수치모델, 예특보, 산업특화-농업
  * 그런데 나중에 보니 하나만 신청이 아니라 한 탭 당 여러개의 api를 신청하는 구조였습니다. 현재는 산업특화-농업 탭만 전체 api 승인을 받아두었습니다. 틈틈히 api를 마저 신청하겠습니다..



* 센티넬 위성정보에서 필요한 데이터

|밴드|이름|해상도|어디에|
|-|-|-|-|
|B04|Red (적색)|10m|NDVI|
|B08|NIR (근적외)|10m|NDVI, NDWI, NDMI 전부|
|B03|Green (초록)|10m|NDWI|
|B11|SWIR1 (단파적외)|20m|NDMI|

B08이 세 지수에 다 들어갑니다. 근적외선이 식물 판독의 핵심입니다.

```
NDVI = (B08 - B04) / (B08 + B04)     잎이 우거진 정도
NDWI = (B03 - B08) / (B03 + B08)     물이 있나
NDMI = (B08 - B11) / (B08 + B11)     잎 속 수분
```

지수는 아니지만 꼭 받아야 하는 것

* **SCL (Scene Classification)** — 픽셀마다 구름·그림자·눈을 분류해둔 값. 이게 없으면 구름 낀 날 값이 그대로 섞여서 평균이 엉망이 된다고 합니다.
* **dataMask** — 영상 범위 밖인지 표시하는 값. 가장자리 처리에 필요합니다.



사용가능한 위성 중 국토위성도 있는데 여긴 데이터 다운로드가 용량도 크고 직접 렌더링 하는 시간이 꽤 걸려서 별로라고 보입니다. (사진 한장 한세트가 10기가입니다..비추)



* 기상청 데이터 / Open-Meteo에서 받아야 할 변수

### 일별 (daily)

```
temperature\_2m\_max          일 최고기온    ← 적산온도 계산
temperature\_2m\_min          일 최저기온    ← 적산온도, 서리 판정
precipitation\_sum           일 강수량      ← 관수 판단
sunrise                     일출          ← 방제 시각
sunset                      일몰
wind\_speed\_10m\_max          최대 풍속      ← 방제 가능 여부
wind\_gusts\_10m\_max          순간최대풍속   ← 강풍 경보
relative\_humidity\_2m\_mean   평균 습도      ← 이슬, 병해 판정
shortwave\_radiation\_sum     일사량        ← "볕이 충분했다"
et0\_fao\_evapotranspiration  증발산량      ← 관수량 계산
```

증발산량이 의외로 중요합니다. 비가 온 양만 보면 부족하고, 얼마나 증발했는지를 빼야 실제 물 부족이 나옵니다.

### 시간별 (hourly)

```
soil\_moisture\_0\_to\_7cm      표층 토양수분   ← 관수 판단
soil\_moisture\_7\_to\_28cm     뿌리층 수분
soil\_temperature\_0\_to\_7cm   지온           ← 파종 가능 여부
wind\_speed\_10m              풍속
wind\_direction\_10m          풍향
relative\_humidity\_2m        습도
```

지온이 파종 판정에 쓰입니다. 농진청 직파 문서에 "일평균 기온 13\~15℃ 이상이면 파종 가능, 19℃ 이상이 적기"라고 나와 있습니다. 기온 말고 지온 기준을 쓰는 작물도 있습니다.

### 옵션 파라미터

```
\&timezone=Asia/Seoul        한국 시각. 필수
\&wind\_speed\_unit=ms         m/s로 받기 ← 기본이 km/h라 헷갈림
\&forecast\_days=16           16일 예보 (기본 7일)
\&models=kma\_seamless        모델 지정
```

단위를 꼭 바꿔야 합니다. 기본이 km/h인데 방제 기준은 m/s를 씁니다. 곡성 데이터에서 5.6 km/h가 나왔는데 그게 1.56 m/s였습니다.

### 과거 자료는 주소가 다릅니다

```
예보   api.open-meteo.com/v1/forecast
과거   archive-api.open-meteo.com/v1/archive
```

과거 쪽은 `\&start\_date=`, `\&end\_date=`를 씁니다. 1940년부터 있습니다.

```
GDD 소급 계산   파종일이 과거인 경우 그 기간 기온
평년값          30년 평균 → "평년보다 1.8도 높다"
```

> \*\*\[보완] 평년값은 기상청 API에도 있습니다\*\*
>
> ERA5로 직접 계산하려 했는데, 기상청 API허브에 공식 평년값이 있었습니다.
> ```
> arcltr\_sfc\_norm.php
>   norm=D(일)/S(순)/M(월)/Y(년)
>   tmst=2021   ← 1991\~2020년 평년
>   항목: 기온 · 강수 · 습도 · 구름 · 증발 · 일사 · 풍속
> ```
> \*\*둘 다 받아 대조하면 검증이 됩니다.\*\* 우리가 ERA5로 만든 평년값이 기상청 공식값과 얼마나 맞는지 보여줄 수 있습니다.

### 격자 만들기

좌표를 콤마로 이으면 여러 지점이 한 번에 나옵니다.

```
\&latitude=35.1,35.1,35.3,35.3
\&longitude=127.1,127.3,127.1,127.3
```

> \*\*\[보완] 바람 흐름 지도를 직접 만들 수 있습니다\*\*
>
> 지인분이 쓰시는 Windy의 하얀 실선은 \*\*관측이 아니라 GFS 수치예보 모델 위에 파티클을 그린 것\*\*입니다. 같은 GFS를 Open-Meteo로 무료로 받고 있으므로, 좌표 격자만 만들면 `leaflet-velocity` 같은 오픈소스로 같은 그림을 그릴 수 있습니다. Windy API를 붙일 필요가 없습니다.
>
> 다만 \*\*텃밭 반경 1km에서는 실선이 전부 같은 방향\*\*이라 볼 게 없습니다. 시군 단위 이상에서만 의미가 있어 2차 범위로 봅니다.

### 우선순위

**1차에 꼭 필요한 것**

```
daily=temperature\_2m\_max,temperature\_2m\_min,precipitation\_sum,
      sunrise,sunset,wind\_speed\_10m\_max,relative\_humidity\_2m\_mean
\&timezone=Asia/Seoul\&wind\_speed\_unit=ms
```

나머지는 나중에. 토양수분·증발산은 관수 조언을 정밀하게 만들 때 붙이면 됩니다.

### 기상청과 겹치는데 왜 둘 다 쓰는지

```
Open-Meteo   빠르고 편함. 토양수분·평년값·다중모델 사용 가능,
             좌표를 이용해 해당 텃밭 기준 기상 데이터 만들기 용이함
기상청       국내 공식 실측. 발표에서 근거로 댈 수 있음
```

둘을 대조하면 검증이 됩니다. "우리 계산이 기상청 실측과 얼마나 맞나"를 보여줄 수 있습니다. 이게 있으면 데이터를 대충 가져다 쓴 게 아니라는 증거가 됩니다.

## 3\. 실제 사용자 서비스에서 LLM 응답이 어떻게 진행되는지



### 판단은 코드, 문장은 Claude

```
\[1단계] 코드가 계산
  기온 누적 → 적산온도 → 생육단계 판정
  강수 합계 → 관수 필요 여부
  농진청 재해 기준과 대조 → 경보 발동
  위성 지수와 교차 확인

\[2단계] 그 결과만 Claude에 넘김

\[3단계] 정해진 형식으로 받아 화면에 표시
```

### 실제 전달 내용 (상주 배추밭 예시)

```python
payload = {
  "작물": "가을배추",
  "파종후": 20,
  "누적GDD": 384, "목표": 797,
  "다음단계": "결구", "남은일수": 8,
  "강수7일": 0.1, "최고기온": 28.8,
  "발동재해": \["가을가뭄"],
  "대책": \["스프링클러 물주기", "짚 덮기"]
}
```

### 시스템 프롬프트 제약

```
- 58세 농민이 읽는 글. 쉬운 말로.
- 입력에 없는 수치를 지어내지 말 것
- 병해충 진단 금지. 관찰 안내까지만.
- 형식: { "요약": …, "할일": \[…], "주의": \[…] }
```

### 출력 예시

```
배추가 잘 크고 있어요. 앞으로 여드레쯤 뒤면 속이 차기 시작합니다.
수확은 10월 중순쯤 될 것 같아요.

→ 오늘 물 주기. 이레 동안 비가 0.1mm뿐이었습니다.
  스프링클러가 있으면 돌리시고, 없으면 고랑에 물을 대주세요.
→ 짚이나 비닐을 덮어두면 땅이 덜 마릅니다.

! 속이 차는 때는 더위에 약합니다. 낮 기온이 아직 28도를 넘고 있으니
  며칠 더 살펴봐 주세요.
```

### 이렇게 나누는 이유

**판단까지 LLM에 맡기면 그럴듯하지만 근거 없는 답이 나옵니다.** 며칠 남았는지, 물이 부족한지는 전부 코드가 정했습니다. Claude는 그 결과를 사람 말로 바꾸는 일만 합니다.

```
조언이 이상할 때 어느 계산이 틀렸는지 추적 가능
"이 조언의 근거는 이 계산식입니다"라고 말할 수 있음
같은 입력이면 같은 판정 — 재현 가능
조언 문장은 농진청 대책표를 옮긴 것이라 출처가 명확
```

### 저장

생성된 조언은 DB에 저장합니다. 저장하지 않으면 어제 뭐라고 했는지 몰라 같은 말을 반복하게 됩니다. 조언을 만들 때 쓴 입력값도 함께 남겨 근거를 추적할 수 있게 합니다.

```sql
INSERT INTO advices
  (cultivation\_id, advice\_date, summary, todos, warnings, input\_snapshot)
```

## 4\. 위성, 기후 사진에 대한 머신러닝 학습은 필요없는지?

머신러닝 학습이 현재로서는 필요없습니다. 기상관련은 대부분 전년도 데이터와 현재의 데이터를 이용한 것이라.. 하지만 사용자의 데이터가 쌓인다면 장기적으로는 머신러닝 학습에 필요한 데이터가 충분히 쌓여 필요하게 될 것으로 보입니다.

```
사진으로 병해충 판별   → 이미지 분류 모델 필요
                        (국가에서 이를 위한 데이터셋을 배포하는것으로 보임)
수확량 예측           → 과거 재배 기록 쌓인 뒤 가능


```

> \*\*\[보완] "지금은 안 된다"의 근거를 조사했습니다\*\*
>
> 통계청 농작물생산조사의 공표 범위를 확인했습니다.
> ```
> 시군별 공표    논벼(쌀)뿐
> 시도별만 공표  채소 · 과수 · 맥류 · 잡곡 (17개 시도)
> ```
> 즉 \*\*텃밭·밭작물 수확량 예측의 정답 라벨이 존재하지 않습니다.\*\*
>
> 실제로 받아본 엽채류 자료에도 문제가 있었습니다.
> ```
> 노지상추      3년간 값이 동일 (서울 2800 → 2800 → 2800)
>               실측이 아닌 표준값으로 보임 → 학습 라벨 부적합
> 노지가을배추   해마다 변동 있음 (부산 11676 → 5803 → 8067)
>               사용 가능하나 시도 단위
> ```
> 상추 같은 자료로 학습시키면 모델이 \*\*"날씨는 수확량과 무관하다"\*\*를 배웁니다. 없는 것보다 나쁩니다.
>
> ```
> 시군 단위 벼 작황 예측   시군별 단수 있음   가능 (2차)
> 텃밭 개별 수확량 예측    라벨 없음          불가
> 채소 수확량 예측         시도 단위까지만    불가
> 사진 병해충 판별         우리 라벨 없음     불가 (공개 데이터셋 존재)
> ```
>
> 가운데 하나가 열려 있지만, 서비스 대상이 소규모 영농인인데 학습 가능한 작물이 논벼뿐이라 \*\*모델을 만들려고 서비스 대상을 바꾸는 것은 본말전도\*\*입니다.
>
> \*\*\[보완] 1차에서 대신 하는 것\*\*
>
> 평년 대비 편차로 판정합니다. 학습이 아닌 통계지만 라벨이 필요 없습니다.
> ```
> 기상청 평년값 (1991\~2020) + Open-Meteo ERA5 (1940\~)
> → 올해 값과의 편차
>
> "이번 봄은 평년보다 1.8도 높습니다"
> "올해 9월 강수량이 평년의 40%입니다"
> ```
> 농민 인터뷰에서도 이 부분이 가장 중요하다는 이야기가 나왔습니다. "평년기온보다 몇 도 이상 올라가고 내려가는지, 그걸로 작물이나 품종 자체가 달라진다."
>
> \*\*\[보완] 1차부터 라벨이 모이게 설계합니다\*\*
>
> 서비스가 돌아야 학습 데이터가 쌓이는 구조입니다. 나중에 붙이려 하면 이미 쌓인 사진에 라벨이 없어 쓸 수 없습니다.
> ```
> 생육일기 체크박스
>   □ 물 줌  □ 거름 줌  □ 약 침  □ 김맴
>   □ 벌레 봄  □ 잎이 이상함  □ 별일 없음
>   → 사진과 함께 저장되면 사진 + 라벨 쌍이 됨
>
> 재배 종료 시 수확량 기록
>   harvest\_date · harvest\_amount · harvest\_unit
>   → 수확량 예측의 정답 데이터
>
> 실패 시 사유 체크
>   □ 병해충 □ 냉해·서리 □ 가뭄 □ 과습 □ 관리 부족
>   → 초보자가 왜 실패하는지의 데이터
> ```
>
> \*\*\[보완] 예상 질문 대비\*\*
>
> "AI 프로젝트인데 학습을 안 하면 AI가 맞나"라는 질문이 나올 수 있습니다.
>
> 학습 모델을 만드는 것과 AI를 쓰는 것은 다릅니다. 자료가 없는데 학습시키면 근거 없는 모델이 나옵니다. 지금은 검증된 농학 공식과 LLM 조합이 더 정확하고, 자료가 쌓이면 학습으로 넘어가는 것이 순서입니다.

## 데모에서 지어낸 것

발표 시 "예시"라고 밝혀야 하는 부분입니다.

```
약도 지형        실제 상주 지형 아님. 위치 표시용 그림
지난 일지 3건    09-09, 09-03, 08-25 — 시나리오용 예시
드론 기준값 5개  풍속 3.0 / 돌풍 5.0 / 습도 60 / 기온 28 / 150분
                → 농민·방제지침 확인 필요
```

나머지는 전부 실측이거나 실측으로 계산한 값입니다.

## 미해결

```
상주 논 관측 좌표   5\~6월 모내기 신호 미검출
                    (5/31 0.62 → 6/15 0.65, 오히려 상승)
                    곡성 실제 논은 0.56 → 0.16으로 명확히 포착
                    → 실제 논이 아니거나 좌표 재확인 필요
```
