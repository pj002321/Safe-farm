# ai-service 최적화

토큰 · 트래픽 · 로딩 세 가지를 따로 적는다. 각 절은 **① 지금 얼마나 드는지 ②
무엇을 바꿨는지 ③ 아직 안 한 것과 그 이유** 순이다. ③ 이 이 문서를 다시 읽을 때
보게 될 부분이다.

구조는 `docs/ARCHITECTURE.md`, 요청 흐름은 `docs/MAIN_FLOWS.md`.

---

## 0. 재기 전에는 고치지 않는다

수치가 없는 최적화는 되돌릴 근거도 없다. 그래서 첫 작업이 **소비량 로그**였다.

| 무엇 | 어디 | 로그 |
|---|---|---|
| 답변 토큰(입력·캐시·출력) | `knowledge/generator.stream_answer` | `[generator] 입력 N(캐시 N) · 출력 N` |
| 근거를 예산에서 잘랐나 | `knowledge/generator._fit_budget` | `[generator] 근거 N개 중 N개만 넣음` |

스트리밍은 기본적으로 usage 를 주지 않는다. `stream_options={"include_usage": True}`
로 켜면 **choices 가 빈 청크**가 마지막에 하나 더 오는데, 예전 코드처럼
`chunk.choices[0]` 로 읽으면 답변을 다 보낸 뒤 IndexError 로 끝난다. 켜는 김에
그 분기를 같이 넣었다.

아래 숫자 중 **실측은 토큰 수뿐**이다. 쿼리 횟수는 코드를 세어 본 값이다.

토큰은 `tiktoken` 의 **`o200k_base`** 로 센다 — `gpt-4.1-mini` 가 쓰는 인코딩이다.
**다른 인코딩으로 세면 숫자가 크게 달라진다.** 같은 문장이 `cl100k_base` 로는
944, `o200k_base` 로는 630 이었다(한글은 차이가 특히 크다). 모델을 바꾸면
`tests/test_prompt_cache_threshold.py` 가 먼저 알려 준다.

## 1. 토큰

### 지금 얼마나

`/v1/ask` 한 번은 LLM 을 **두 번** 부른다.

| 호출 | 고정 입력 | 변동 입력 |
|---|---|---|
| `plan`(밭 조회 필요?) | `PLAN_SYSTEM` 135 + `TOOL_SPECS` 79 = **214 토큰** | 질문 + 지난 대화 |
| `generate`(답변) | `SYSTEM_PROMPT` **1,087 토큰**(캐시 대상) | 근거 + 밭 정보 + 지난 대화 + 질문 |

변동 입력의 대부분은 근거다. 근거는 matches(top-5)에 같은 문서의 앞뒤 조각을 더한
것이라 본문이 **1.8배**로 는다(`knowledge/vector_store.neighbors`).

### 바꾼 것

**① 밭 없는 질문은 `plan` 에서 LLM 을 안 부른다** (`graph/nodes.plan`)

라우팅 결과가 원래 `route = "tool" if tool_calls and plot_id else "rag"` 였다.
`plot_id` 가 없으면 LLM 이 뭐라 답하든 `rag` 로 고정 — **묻고 버리는 왕복**이었다.
첫 화면 질문과 일반 재배법 질문이 전부 여기 걸린다.

- 그 질문에 한해 LLM 호출 2회 → 1회.
- 판단 자체는 그대로다. 밭이 있으면 예전처럼 LLM 이 정한다
  (`tests/test_plan_skips_llm.py` 가 양쪽을 다 고정한다).

**② 근거에 글자 예산** (`CONTEXT_CHAR_BUDGET`, 기본 12,000자)

`build_context` 가 예산을 넘으면 **뒤에서부터 버린다.**

- 뒤가 맞는 이유: 앞은 리랭크까지 끝난 matches, 뒤는 덤으로 붙인 이웃 조각이다.
  거리순으로 다시 정렬해 자르면 1위 근거가 빠질 수 있다.
- **조각을 중간에서 자르지 않는다.** 문장이 끊긴 근거는 모델이 뒤를 지어내게 만든다.
- 예산을 넘겨도 **첫 조각은 항상 넣는다.** 근거 0건은 "검색 실패" 의 뜻이고, 그때는
  일반 지식 답변이 나간다 — 예산 때문에 그 상태를 만들면 안 된다.
- `0` 을 주면 무제한이다. 상한이 답을 망쳤는지 비교할 때 쓴다.

**③ 출력 상한** (`ANSWER_MAX_TOKENS`, 기본 800)

출력 토큰이 입력보다 비싸고, 화면 체감은 첫 글자가 아니라 **마지막 글자**까지의
시간이 정한다. 800 은 "근거 하나에 한두 문장" 규칙으로 나오는 답의 두 배쯤이다 —
상한에 닿으면 문장 중간에서 끊기므로 빠듯하게 잡지 않는다.

**④ 프롬프트 캐시 문턱 넘기기** (`SYSTEM_PROMPT`, 630 → 1,087 토큰)

> ⛔ **이 항목은 2026-09-20 실측으로 뒤집혔다. 아래 "④ 는 실측에서 뒤집혔다" 를
> 먼저 읽을 것.** 여기 적힌 전제와 수치는 당시 판단 기록으로만 남긴다.

OpenAI 자동 프롬프트 캐시는 **앞부분 1,024 토큰**부터 걸린다. 비율이 아니라
0/1 이다 — 한 토큰 모자라면 아무것도 안 걸린다. 요청마다 글자까지 같은 부분은
`SYSTEM_PROMPT` 하나뿐이라(뒤 user 메시지는 질문·근거·밭 정보라 매번 다르다)
캐시가 걸리느냐는 이 상수 길이가 전부다.

> **먼저 잘못 쟀다.** 처음에 944 토큰으로 적어 뒀는데 `cl100k_base` 로 센 값이다.
> 우리 모델은 `gpt-4.1-mini` 라 `o200k_base` 를 쓰고, 한글은 인코딩 차이가 커서
> 실제로는 **630 토큰**이었다. 모자란 양이 80 이 아니라 394 였다.

빈 말로 394 토큰을 채우면 규칙만 흐려진다. 그래서 **매 요청 보내면서 설명은 안
하던 것**을 올렸다. 셋 다 그 자체로 답변에 쓸모가 있다:

| 더한 것 | 토큰 | 왜 쓸모가 있나 |
|---|---|---|
| 출처 7종 이름 | 80 | 모델이 `[일반 지식]` 처럼 없는 라벨을 지어내던 자리 |
| `참고값` 키 사전 | 280 | `base_temp` 가 ℃ 인지 모델이 짐작했다. `gdd_to` 미포함도 여기서 알린다 |
| 형식 예시 1개 | 100 | 줄바꿈·출처 위치 규칙이 말로만 있었다 |

- 출처 목록은 `SOURCE_LABELS` 에서 만든다 — 라벨을 고쳐도 따로 놀지 않는다.
- **1,087 로 맞춘 이유:** 캐시 구간은 128 토큰 단위(1,024 → 1,152)다. 넘치는
  만큼은 캐시 없이 제값이라 1,024 를 막 넘긴 자리가 가장 이득이다.
- `tests/test_prompt_cache_threshold.py` 가 이 선을 지킨다. 문구를 다듬다 길이가
  줄어도 답변은 멀쩡해서 아무도 모르고 청구서에만 나타난다.

> ⚠ **`SYSTEM_PROMPT` 를 늘렸으니 답변이 바뀐다.** 이 상수는 실패 사례를 보고 한
> 줄씩 붙여 온 것이라, `pipeline/doc/golden.py` 를 돌려 hint 수가 떨어지지 않는지
> 보고 머지한다. 떨어지면 되돌리는 쪽이 맞다 — 캐시는 돈이고 정답률은 제품이다.

- 이미 되어 있는 것: `build_context` 의 `sorted(meta)`. JSONB 키 순서가 요청마다
  달라지면 같은 질문에도 프롬프트가 달라져 캐시가 영영 안 걸린다. **지우지 말 것.**

#### ④ 는 실측에서 뒤집혔다 (2026-09-20)

before/after 측정을 돌려 보니 `/v1/ask` 14건이 전부 `llm_cached = 0` 이었다.
원인을 따라가 보니 **위에 적힌 "1,024 를 넘기면 걸린다" 가 틀렸다.**

`usage.prompt_tokens_details.cached_tokens` 를 직접 읽어 잰 값이다
(`gpt-4.1-mini`, 스트리밍, 매번 다른 본문):

| system 공유 | 총 prompt | 뒤쪽(가변) | cached |
|---|---|---|---|
| 1,511 | 1,541 | 30 | **1,408** |
| 5,376 (본문까지 동일) | 5,595 | 219 | **5,376** |
| 1,511 | 2,440 | 929 | 0 |
| 1,511 | 3,800 | 2,289 | 0 |
| 1,511 | 8,400 | 6,900 | 0 |

**공유 구간의 길이가 아니라 전체에서 차지하는 비중이 결정한다.** 앞 1,511 토큰이
같아도 뒤에 900 토큰만 다른 내용이 붙으면 한 건도 안 걸린다. 문턱을 넘기려고
`SYSTEM_PROMPT` 를 1,087 로 맞춰 둔 것도, 1,511 로 늘려 본 것도 소용이 없었다.

그래서 이 앱의 두 LLM 호출은 **둘 다 캐시 대상이 아니다**:

- `generate` — 밭 정보·참고 자료가 질문마다 검색돼 붙는다. 공유 구간을 다수로
  만들 방법이 없다. 구조상 불가능하다.
- `plan` — 고정부가 `PLAN_SYSTEM` 135 + `TOOL_SPECS` 79 = 214 토큰뿐이다.
  1,024 를 넘기려면 4배로 부풀려야 하고, 75% 할인을 받아도 지금 값과 본전이다.

`SYSTEM_PROMPT` 길이는 이제 **캐시와 무관하게** 정한다. 짧게 쓰는 게 맞다 —
캐시가 안 닿으니 늘린 만큼 매 요청 제값이고, 길수록 뒤쪽 규칙이 묻힌다.
`tests/test_prompt_cache_threshold.py` 의 길이 하한·상한 검사는 근거를 잃었다.

> 캐시를 노려 늘렸던 규칙(줄바꿈 함정·대괄호 오용)은 **내용 근거는 따로 있다** —
> 2026-09-19 답변 67건 중 줄바꿈 위반 54건(81%), 없는 라벨 날조 10건(15%).
> 캐시와 별개로 다시 검토할 값이라 `stash` 에 남겨 뒀다.

### 안 한 것

**`neighbors` 폭 줄이기.** `width=1` 을 0 으로 하면 본문이 절반이 되지만, 이 기능은
골든 hint 를 29→31 로 올린 장치다(정답이 뽑힌 조각 **옆**에 있던 사례). 토큰을
줄이자고 정답률을 되돌리지 않는다. 길이 문제는 위의 예산으로 막는다.

## 2. 트래픽

### 지금 얼마나

재배 건이 있는 밭으로 `/v1/weather/plot` 을 한 번 부르면 DB 왕복이 **17회쯤**이다.
그중 절반이 같은 질문의 반복이었다.

```
usable_crop_of_variant  ×3   ← daily_gdd_series · crop_interpretation · compute_plot_growth
lead_growing            ×3      셋이 저마다 필요해서 각자 부른다
variant_by_id           ×2
```

화면은 이 엔드포인트를 **밭마다** 부른다. 밭이 셋이면 그대로 3배다.

### 바꾼 것

**① 요청 범위 마스터 캐시** (`core/request_cache.py`)

`Session.info` 에 붙는 캐시다. `repo/crop.py` 의 `variant_by_id` ·
`usable_crop_of_variant` · `stage_by_order` 가 쓴다. 17회 → 13회.

> **2026-09-20 추가 — `stage_count_and_last_order` · `hazard_temp_limits` 도 쓴다.**
> 작업카드 배치가 밭의 **작물마다** 판정하게 바뀌면서(교안 §2-B) 이 둘이 밭 수만큼
> 되풀이됐다. 구조를 더한 게 아니라 위 셋과 같은 자리에 빠져 있던 것을 채웠다 —
> 둘 다 정적 마스터(`crop_stages` · `crop_disaster_rules`)이고 돌려주는 값도 불변
> 튜플이다(`hazard_temp_limits` 는 알맹이를 `_hazard_temp_limits` 로 떼어 감쌌다).
>
> 자정 배치 한 번(밭 23개 · 재배 20건) 실측:
>
> ```
> 쿼리 143건 → 127건        되풀이 29건 → 13건        약 0.5초 → 0.21초
> ```
>
> (왕복 1회가 16ms다 — 데이터 양이 아니라 **지연**이라 건수가 곧 시간이다.)

세션이 닫히면 같이 사라지므로 **비우는 코드가 없다.** 지키는 선 둘:

- **정적 마스터만 담는다**(`crops` · `crop_variants` · `crop_stages`). 사용자
  데이터를 담으면 같은 요청 안에서 쓰기 뒤의 읽기가 옛 값을 본다. 자정 배치는
  세션 하나로 밭 수백 개를 도니까 "요청 하나"가 배치 전체다.
- **세션보다 오래 사는 캐시에 ORM 객체를 넣지 않는다.** detach 된 뒤 속성을 읽으면
  `DetachedInstanceError` 다. 세션 밖까지 들고 가야 하면 `repo/station.py` 처럼
  값 dataclass 로 베껴 담는다.

자정 배치에서 효과가 더 크다. 밭 N개 × 마스터 조회 → **서로 다른 숙기 수**만큼으로
준다. 같은 작물을 기르는 밭이 많을수록 많이 준다.

**② Open-Meteo 예보 캐시** (`pipeline/open_meteo_client.py`, `FORECAST_CACHE_TTL` 600초)

좌표를 소수점 3자리(≈100m)로 반올림해 캐시한다. 밭 총평은 사용자의 밭을 차례로
돌며 예보를 받는데, 한 사용자의 밭은 대개 같은 동네다 — N회가 1회가 된다.

- **성공만 담는다.** 장애 응답을 담으면 TTL 이 끝날 때까지 복구돼도 실패로 보인다.
- **사본을 준다.** 원본을 그대로 주면 부르는 쪽이 한 번 손대는 순간 다음 요청까지
  틀어지는데, 그 인과는 로그로 못 쫓는다.
- **개수를 막는다**(`CACHE_MAX_ENTRIES` 256). 배치가 전국을 돌면 좌표가 수천 개다.
- **동시 요청은 각자 받아 온다.** 막으려면 잠금을 HTTP 까지 넓혀야 하는데, 그러면
  외부 API 가 느릴 때 뒷 요청이 전부 거기 매달린다.
- 담기는 건 좌표와 공개 기상값뿐이다. **사용자 정보가 섞이지 않는다.**
- `FORECAST_CACHE_TTL=0` 이면 캐시를 끈다. 예보가 이상할 때 캐시 탓인지 가르는 스위치.

### 이미 되어 있던 것 — 지우지 말 것

| 무엇 | 어디 | 없으면 |
|---|---|---|
| 관측소 109행 프로세스 캐시 | `repo/station.py` | 밭 카드마다 전체 조회 |
| 작물 이름 집합 캐시 | `knowledge/retriever.known_crops` | 질문마다 3표 union |
| 참조 CSV `lru_cache` | `service/sigungu_ref` 등 | 요청마다 파일 파싱 |
| `joinedload(Chunk.document)` | `knowledge/vector_store` | top_k=10 에 SELECT 11번 |
| 현재·시간별·일별 한 번에 | `open_meteo_client.fetch_forecast` | 밭당 왕복 3배 |
| 답변은 스트림 끝나고 한 번 저장 | `api/ask._sse` | 커밋이 토큰 수만큼 |

### 안 한 것

**`lead_growing` 3회 중복.** 캐시로 덮지 않았다. `cultivations` 는 사용자 데이터고,
같은 요청 안에서 바뀔 수 있는 표에 캐시를 걸면 조용히 옛 값을 보게 된다. 제대로
고치려면 `daily_gdd_series` · `crop_interpretation` · `compute_plot_growth` 가
재배 건을 **인자로 받게** 바꿔야 한다 — 서비스 셋의 시그니처와 호출부 전부가
움직이는 일이라 따로 잡는다.

**`pest_bulletins_for` 8회 중복** (2026-09-20 발견 · `feature/cultivation-detail`).

작업카드가 작물마다 판정하게 되면서 드러났다. 자정 배치 한 번에 **같은 인자로 8번**
더 나간다 — 상추 4밭 · 고추 3밭처럼 **같은 작물을 기르는 밭이 많아서**다. 약 0.13초.

담아도 될 조건은 갖췄다. `pest_bulletins` 는 발생정보(2023~2026) 정적 마스터이고,
`pest_names_for` 가 돌려주는 값은 `tuple[str, ...]` 이라 ORM 객체가 아니다.

**그런데 안 했다.** 조회가 `repo/bulletin.py` 에 있고 그 파일엔 아직 `memo` 를 쓴
자리가 없다 — 이 절의 판단(무엇을 담고 무엇을 안 담나)을 세운 사람이 정하는 게 맞다고
보아 넘긴다. 하게 되면 **열쇠에 `today` 를 넣어야 한다**: 이 조회는 월·일로 구간을
맞추는데, 자정을 넘겨 도는 배치에서 날짜가 바뀐다.

**같은 기간을 두 번 읽는 `temps_since`.** `compute_plot_growth` 는 파종일부터,
`daily_gdd_series` 는 최근 14일부터 읽는다. 뒤가 앞의 꼬리라 한 번에 읽어 나눌 수
있지만, "꼬리를 잘라 쓴다"는 가정이 파종일이 14일 안쪽일 때 어긋난다. 위의
시그니처 정리와 같이 한다.

## 3. 비동기 · 로딩

### 지금 얼마나

`/v1/ask` 의 첫 글자까지 걸리는 시간은 이 직렬 사슬이 정한다.

전에는 이 직렬 사슬이 `/v1/ask` 의 첫 글자까지 걸리는 시간을 정했다.

```
plan(LLM 왕복) → retrieve(임베딩 1회 + 벡터 2쿼리) → generate(첫 토큰)
```

`retrieve` 는 **`plan` 의 결과를 하나도 안 쓴다.** 그런데 뒤에 서 있었다.

### 바꾼 것

**① 밭 없는 질문은 `plan` 왕복이 통째로 빠진다**(1절 ①). 첫 글자까지의 시간이
LLM 왕복 하나만큼 줄어든다 — 토큰 절약보다 이쪽이 체감이 크다.

**② `plan` 과 `retrieve` 를 나란히 돌린다** (`graph/graph.build_graph_default`)

```
START ┬─ plan ──(밭 조회 필요?)── run_tools ─┐
      └─ retrieve ───────────────────────────┴─ generate ─ END
```

밭 있는 질문에서도 임베딩·벡터 검색이 `plan` 의 LLM 왕복 뒤에 줄 서지 않는다.
LangGraph 는 같은 슈퍼스텝의 동기 노드를 스레드 풀에 올리므로 **정말로 같이 돈다**
(`tests/test_ask_graph_parallel.py` 가 두 노드가 겹치는지 실제로 확인한다).

돌려 보고 나서야 안 것 둘:

- **합류 노드는 들어오는 엣지를 전부 기다려 주지 않는다.** 먼저 도착한 `retrieve`
  만으로 `generate` 가 한 번 돌고, 늦게 온 `run_tools` 때문에 또 돈다. tool 경로에서
  **답이 두 번 흐르고 첫 번째는 밭 정보가 없다.** `add_node("generate", generate,
  defer=True)` 가 막는다 — 빼면 그대로 재현된다.
- **`route_after_plan` 이 "retrieve" 를 가리키면 안 된다.** `retrieve` 는 START 에서
  이미 출발해 있어서 두 번 돈다. 이제 "generate" 를 돌려준다.

⚠ **`plan` 에서 DB 를 만지면 안 된다.** `retrieve` 와 다른 스레드로 도는데 `Session`
은 스레드 안전하지 않다. 지금 db 를 쓰는 건 `retrieve` 와 `run_tools` 뿐이고, 이
둘은 슈퍼스텝이 달라 겹치지 않는다.

### 이미 되어 있던 것

- **SSE 는 `meta` 를 맨 앞에 보낸다.** 프런트가 `historyId` 를 먼저 받아야 피드백
  대상을 알고 잔여 횟수를 곧바로 줄여 보여준다.
- **예외가 나면 `error` 이벤트를 반드시 보낸다.** 조용히 끊으면 프런트는 짧은
  답변을 정상 완료로 읽는다.
- 리포트는 외부 API(예보·특보)가 실패해도 계속 간다. 로딩이 외부 장애에 묶이지 않는다.

### 안 한 것 — 다음 후보

**`/v1/weather/plot` 의 캐시 키.** 소유 확인은 넣었다(§5) — `user_id` 를 받아
`owned_plot` 을 탄다. 남은 건 Next 쪽이다. **`user_id` 가 쿼리에 붙으면 Next 의
데이터 캐시 키가 바뀐다.** 지금 밭 단위로 공유되던 응답이 사용자 수만큼 쪼개진다.

2절 ② 의 좌표 캐시가 ai-service 쪽에서 그 손해를 상쇄한다 — 같은 좌표면 외부
왕복은 그대로 한 번이다. **순서는 이미 맞다**(서버 확인 먼저, 호출부 나중).
호출부를 고친 뒤 갈라진 캐시의 실제 호출 수를 보고 `WEATHER_REVALIDATE_SEC` 를
정한다.

**밭 총평의 밭별 처리 병렬화.** `build_farm_summary_inputs` 가 밭을 차례로 돈다.
스레드로 나누면 빨라지지만 **`Session` 은 스레드 안전하지 않다** — 같은 세션을
나눠 쓰면 커서가 엉킨다. 밭마다 세션을 새로 열면 커넥션 풀(`DB_POOL_SIZE` 5)이
먼저 마른다. 지금은 이 경로의 가장 큰 비용이 외부 예보 호출이고, 그건 2절 ② 의
캐시가 같은 동네 밭을 한 번으로 줄여 준다.

## 4. 손대면 안 되는 것

성능을 이유로 지우기 쉬운데 지우면 조용히 틀리는 것들이다.

| 무엇 | 어디 | 지우면 |
|---|---|---|
| `set local hnsw.iterative_scan` | `knowledge/vector_store` | 필터 걸린 검색이 **0건**이 된다 |
| `sorted(meta)` | `knowledge/generator.build_context` | 프롬프트가 매번 달라져 캐시가 영영 안 걸린다 |
| `[출처 · 제목]` 머리 | 같은 곳 | 다른 문서의 참고값을 이 제목에 갖다 붙인다 |
| 후보 50 · 소스당 2 · top-5 | `knowledge/retriever` | 실측으로 정한 값이다. 후보를 줄이면 정답이 순위 밖으로 나간다 |
| `deleted_at is null` | `repo/*` | 지운 밭이 살아난다 |
| `generate` 의 `defer=True` | `graph/graph` | tool 경로에서 답이 두 번 흐른다 |
| `SYSTEM_PROMPT` 길이 | `knowledge/generator` | 1,024 토큰 아래로 내려가면 프롬프트 캐시가 통째로 사라진다 |
| `plan` 이 DB 를 안 보는 것 | `graph/nodes.plan` | `retrieve` 와 같은 `Session` 을 두 스레드가 잡는다 |
